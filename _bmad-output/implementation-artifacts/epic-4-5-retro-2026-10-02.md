## The dominant finding

**138 review patches across seven stories. 50 of them — 36% — were comments or records asserting
behaviour the code does not have. Present in 7 stories out of 7.**

| Theme | Count |
|---|---|
| Prose contradicting its own code | 50 |
| Stale client cache / socket payload omitting a field | 22 |
| Concurrency and races | 10 |
| Silent failure — something fails and nobody is told | 9 |
| Verification that could not have failed | 8 |
| Dead or unreachable controls | 5 |

(Categories overlap; a finding can be two things.)

### Why it did not go away when we looked for it

By Story 4.3 the pattern was named and every subsequent review hunted it specifically. It still appeared
in every story, and in the last two it **moved from code comments into the Dev Agent Records**:

- Story 5.0's record claimed the crash loop was bounded by counting attempts at claim time. It was not —
  dead-lettering only ran on a rejected delivery, so a job that crashed the worker was revived every two
  minutes forever. The claim was the *only* justification given for that design choice.
- Story 5.2's record said "four of Story 5.0's checks were edited" (three), and "no queue check was
  weakened" (one was weaker in kind).

Both were caught by the Acceptance Auditor layer, which reads the record against the code. Without that
layer they would have shipped as project history.

### The mechanism, as best I can see it

The explanation gets written **while** the code is being written — when it describes an intention. Then
the code moves and the prose does not. Worse, the prose is detailed and argued, which makes it harder to
doubt on re-reading: a bare comment gets checked, a persuasive one gets believed.

**Action (Teran's call, 2026-10-02): write the comment last.** Comments explaining *why* are written
after the behaviour is verified, not alongside the code. The Dev Agent Record is written **from the
verification output**, not from memory.

## The pattern that is more dangerous than its count

**22 findings were a socket payload omitting a field the client needed.** Every one has the same shape:
the client patches its cache rather than refetching (correct — AC-4 of Story 3.2 forbids refetching the
world on an event), so **a field missing from a payload silently keeps its stale value, permanently,
until something unrelated triggers a refetch.**

The list: `unavailableReason`, `groupTableLabels`, `totalPaisa`, `roundItemCount`, and most recently a
seated counter sale whose table card stopped refreshing for the rest of service because the emit branched
on `kind` instead of on whether tables were attached.

There is no compiler for this and no runtime error. The only thing that has ever caught it is a review
layer with project access asking "what does the client do with the field you left out?"

**Action: when any socket payload type gains or loses a field, the patch site in the client is part of
the same change** — and the story's verification asserts the patched row, not just the emit.

## What went well, and should not be lost

- **Scripted verification against a real database and a real server.** The 12-way concurrent seat POST,
  five simultaneous identical sends, two workers racing for one print job, a fake TCP printer that can
  refuse / hang / drop / answer back. None of that is reachable by clicking, and each caught something.
- **Letting the database decide races.** `FOR UPDATE SKIP LOCKED`, partial unique indexes, `23505`
  caught *by index name*, row locks. The one place a pre-check was written to merely *look* atomic
  (Story 3.9's last-table guard) was caught in review and moved into the database.
- **Measuring instead of arguing.** Late, but decisive: the ESC/POS "polite refusal" gap was settled by
  probing socket event timings (write callback at 6ms, peer FIN at 9ms) rather than by reasoning. That
  is the only reason it is documented as a known limitation instead of shipped as a false fix.
- **Three independent review layers.** Blind, Edge-Case and Acceptance each found things the others
  missed. The Auditor in particular is the only one that reads the record against the code — which is
  what caught the two false claims above.

## Honest gaps carried out of these epics

1. **Nothing in Epic 4 or 5 has ever been clicked in a browser.** Every tap on the order screen, every
   floor card, the seat selector, the modifier sheet, the send flow, and the printer alert banner's five
   states are verified by script and by reading only.
   **Action (Teran's call): a browser pass before Epic 6 starts.**
2. **Nothing has ever printed on paper.** No hardware exists. The code page (CP437 assumed), the
   `GS V 66` partial cut, and 48 columns are each one constant, unproven until a printer is bought.
3. **A polite refusal is indistinguishable from a successful print** at the TCP layer. Measured,
   documented, pinned by a `KNOWN GAP` check, logged for decision.
4. **Nine stories across Epics 1–3 sit at `review`, and 3-2 at `in-progress`.** They were implemented
   long ago; the table grid has been rewritten twice since. The board does not currently tell the truth
   about them.

## Preparing for Epic 6 — Bill Settlement & Payment Recording

Checked against the schema and services as they stand.

**Ready:**

- `payment_records(amount_paisa, method, session_id, staff_id, covered_seat_slots)` exists — per-seat
  settlement (6.4) is expressible.
- `order_events` carries `unit_price_paisa` as quoted, so a bill is a sum over committed rows.
- `dishTotalPaisa` already computes a session's running total for the floor card.
- `closeSession` exists with `settled` **deliberately excluded** from the client-facing reasons —
  Story 6.5 owns that path, as planned.

**Gaps to settle before or during Epic 6:**

1. **Service charge has no column.** `tenant_config` has `tax_rate_percent` only. The order screen's
   mockup shows "Service 10%", and the floor card's running total is NOT a bill — no service, no tax,
   no comps. Story 6.2 cannot produce a correct bill without deciding: a column, a rule for whether it
   applies to comped items, and a line on the bill. **Potential epic update — flag before 6.2.**
2. **Story 2.4 (financial re-auth) is deferred post-demo, but `financial_action_reauth` defaults to
   `true`** and Epic 6 is the financial epic. Either 2.4 returns to scope or the flag goes false for the
   demo — decide before 6.5 records a payment.
3. **Comps are Epic 7, but a bill has to render one.** 6.2 should define what a comped line looks like
   on a bill even though nothing writes comps yet.
